# Durable Android task checkpoints and one-time action ledger

## Boundary and upstream reference
The LangGraph.js backend remains planning-only, without native device controls
or a server-side checkpoint store. Device-side at-most-once reservations follow
LangGraph's checkpoint and replay design, but intentionally run locally:
- https://github.com/langchain-ai/langgraphjs/blob/main/libs/checkpoint/src/base.ts
- https://github.com/langchain-ai/langgraphjs/blob/main/libs/checkpoint/src/memory.ts
- https://github.com/langchain-ai/langgraphjs/blob/main/docs/docs/concepts/functional_api.md

Deep Agents's filesystem permissions are NOT a phone security policy: its
default on unmatched rules permits operations. Android tools remain default-deny.

## Encrypted, durable storage
`AgentJournalModule.kt` stores AES-256-GCM ciphertext in private Android
SharedPreferences. The AES key is generated by Android Keystore. Every record
uses a fresh random 96-bit IV; preference identifiers are SHA-256 hashes.
The app disables OS auto-backup. Synchronous `commit()` precedes tool dispatch;
storage failures block execution. Hardware-backed key storage is not guaranteed
by every phone and does not imply biometric authentication.

## Action state transitions
- Low-risk: UNSEEN -> CLAIMED (durable) -> SETTLED or UNCERTAIN.
- Approval-required: UNSEEN -> PENDING -> APPROVED (human button) -> CLAIMED
  (durable) -> SETTLED or UNCERTAIN.
- CLAIMED, SETTLED, UNCERTAIN cannot be claimed again. If an action started
  but its outcome was never recorded, it is blocked on restoration.
- Approvals are scoped to the exact session ID, call ID, tool ID and canonical
  arguments; one approval cannot be used for a different recipient or message.
- The model and remote tools have no direct access to the Android journal.

## Recovery
The app assigns a native UUID to every task, stores an encrypted checkpoint
with the original request and observations, and only reads the latest session
after restart. It does NOT automatically restart. The owner must select Resume.
Permissions are checked again. Already-reserved actions are never replayed.

## Limitations
- Kotlin compilation is not a physical-device test: process-death, restore,
  corruption, and keystore-reset acceptance tests remain to be performed.
- Maximum snapshot is 64 KiB; long histories require an audited encrypted DB.
- A retention/deletion UI is not yet implemented. Action dedupe tombstones
  cannot be deleted blindly, as that can cause duplicate sends on replay.
- No message sending tool is enabled yet. The Android **Test approval**
  command exercises the approval UI with a simulated no-op tool only.
- Local native Android persistence is not the same as LangGraph server-side
  thread checkpointers, which remain a future milestone.

## Android emulator instrumentation
The `SecureJournalAndroidTest.kt` suite exercises actual Android Keystore
encryption and SharedPreferences persistence across native module instances,
one-time approval consumption, rejection of altered fingerprints, and denial
of claims after an uncertain outcome. A separate opt-in/changed-paths GitHub
Actions emulator job runs API 35 with `connectedDebugAndroidTest`.
Source-code and JVM mock tests alone cannot prove native encryption. Emulator
tests are stronger than static checks but still do not replace a physical
phone process-death and OS-background acceptance run.

## Concurrency and crash consistency hardening
The Android journal uses a single companion-object mutex across native module
instances in its process, preventing two React Native bridges from concurrently
claiming the same action. Checkpoint and latest-session pointer are stored in
the same encrypted SharedPreferences commit. Emulator instrumentation races
12 module instances to assert only one claim is granted. This is still NOT
cross-process/distributed transaction support; the Android manifest does not
start a separate process for this module.
